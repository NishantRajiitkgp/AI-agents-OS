## Context

This is the anti-invention control, and it is the reason `satisfies` is a field at all. A task
that satisfies nothing live is a task somebody made up — the observed failure mode where an
agent generates plausible work that no requirement asked for, and the backlog grows faster
than anyone can audit it.

`STATE-6` wants malformed state refused at the boundary and `STATE-7` wants identifiers unique
across the repository. Both are currently half-met: the schema of a single file is checked,
but nothing checks that the references between files resolve. A dangling `satisfies` is
precisely the shape of error that looks fine per-file and is wrong in aggregate.

It is also the last piece of validation that does not need a binary, and `aios next` at
`M1-10` treats an unresolvable `satisfies` as a hard error, so the selector cannot be built
until the resolver it depends on is trustworthy.

## Outcome

Both verify commands exit zero. Nine failure modes have fixtures; four mutations of the
validators were each caught by the suite. `duplicate_check` was added by `M4-04` after this
work finished: both searches happened — the second is why `aios_state.py` exists rather than a
third parser — but a reconstructed record is weaker than one written first, and this is the
last task that can have one.

Held at `review` rather than `done`. A verification record needs the commit the commands ran
against (04 §3.4) and this repository has no commits yet, so the record cannot be written.
This is the control working: `done` is a state the evidence reaches, not a claim, and the
evidence is genuinely incomplete. Moves to `done` once the remote exists.
