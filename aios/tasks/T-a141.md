`TestTheProofThatIsStillOwed` asserted the *blocked* state: it failed the moment an
executable appeared anywhere it looked, and its failure message said what was then owed —
point the contract checks at the real subject and run the cross-ecosystem proof. That was the
honest thing to write while `M1-08` was held, because a skipped test is invisible in a green
run and this was the one check nobody could afford to forget.

The proof has now run. The `v0.1.0` release built four platform binaries, deleted the Rust
toolchain from the runner and refused to continue until `cargo`, `rustc` and `rustup` were all
absent, then called the shipped binary from a dependency-free Node project and re-ran this
suite against it. It found three real contract violations while doing so, which is what the
tripwire existed to make happen.

So the test has done its job and is now the opposite of what it says: it asserts that the
thing it was demanding has not happened. Its own message instructs deleting it.

The other three checks in the class do not depend on the binary being absent — they read the
source for the contract's exit codes and for any `process::exit` that would bypass them — so
they stay, under a name that describes what is left.

The second verify command is the one that matters. Without it, deleting nothing and letting
the suite pass would satisfy this task.

`satisfies` names `STATE-6` for its second clause — the system distinguishes an inability to
run a check from a check that ran and passed — because that distinction is what ADR-013 §2
specifies and what this suite is the executable check for. The mapping is indirect and worth
saying out loud: there is no requirement area for the invocation contract, only `state.md`,
so nothing here covers cross-ecosystem invocation on its own terms. Inventing a requirement to
justify a cleanup would be worse than naming the one this suite actually guards, but the gap
is real and belongs on the list.
