## Context

Carried over from `M2-01` and `M2-02`, which were one piece of work described as two.
`.github/CODEOWNERS` is written, covers every entry in `protected_paths`, and now names a
resolvable handle rather than the placeholder — but a CODEOWNERS file changes nothing at all
until "Require review from Code Owners" is switched on for the default branch.

That gap is the reason `check-codeowners.py` prints what it cannot check instead of implying
otherwise. GitHub does not reject an owner it cannot resolve: it drops the rule and reports
the file as valid, so a CODEOWNERS naming nobody is indistinguishable from one naming
somebody. The same shape of failure applies one level up — a covered file list with no branch
protection behind it reads as a control that works right up until it is tested.

`GUARD-1` is the containment requirement everything else in the gate layer rests on, and
`GUARD-2` is why this task cannot be satisfied by anything committed to the repository. The
settings live with the forge; the repository can only record them.

## Outcome

The declaration, the check and the runbook are written; the settings are not on yet, and the
first verify command reports exactly that. It reads the forge and currently says the branch
has no protection at all.

`check-codeowners.py` claimed this was not checkable from here. It is: the `protected` flag is
public, and the per-setting detail is served to any token that can read the repository, which
CI mints per run. The script reports which of the two it managed, because a check that says
"protected" when it only learned "not obviously unprotected" is the failure mode this whole
layer exists to avoid.

Reaches `done` when the settings are on and the check goes green, which is a click this
repository cannot make on its own behalf — which is the point of the layer.
